# 実機検証記録

2026-10-27（日本時間）。Windows x64環境、接続済みのSony CECH-ZD1 J、既存のWinUSBバインド、内蔵B-CASを使用しました。アンテナや減衰器の条件を変えた比較は行っていません。チャンネル番号は物理チャンネルです。

## 選局

測定ツールは、coax由来の制御処理を切り出した `cechctl` です。coaxデーモン全体と新BonDriver全体のA/B測定ではなく、同じハードウェア制御経路の自動探索とパラメーター再利用の比較です。

| 条件 | TS到着までの実測 |
| --- | --- |
| 自動探索経路、20chの初回 | 約2.5秒 |
| 自動探索経路、同じ20chの再選局 | 1.481〜1.698秒（3回） |
| パラメーター再利用、同じ20chの再選局 | 1.002〜1.014秒（3回） |
| 18→20→23chの反復、キャッシュ済みの切替 | 1.133〜1.222秒、平均1.166秒（12回） |
| 18→20→23ch、初めて選ぶ周波数 | 1.595〜2.623秒（3回、最初の校正を含む） |

初回のチューナー校正は維持しています。ホストを閉じて開き直すと、この校正と伝送パラメーターの探索が再び必要です。同じホストでチャンネルを変えるときの改善値を、初回起動の短縮値として扱うことはできません。

反復切替15試行はすべてフルセグでロックしました。各試行でTEI・連続性エラー・不正TS・PAT CRC異常・同期喪失は0でした。PATのTSIDは18chが32707、20chが32224、23chが32230で、各試行内の混在はありませんでした。

停波中だった13chへの選局は約0.57秒で失敗を返し、その後20chへ復帰できました。無信号の試行を含む試験コマンドは、仕様どおり終了コード1を返しています。

## 連続受信とカード通信

20chの受信CLIを300秒動かした結果です。

| 項目 | 結果 |
| --- | --- |
| 受信バイト数 | 647,545,132 |
| TSパケット数 | 3,444,389 |
| TEI / continuity / 不正TS | すべて0 |
| 受信中の同期喪失 / PAT CRC異常 | いずれも0 |
| 空受信タイムアウト | 0 |
| 最大データ到着間隔 | 43ms |
| 初期同期までの端数破棄 | 50バイト |
| 確認したTSID | 32224のみ |

BonDriverの公開API試験では、x64とx86のDLLを実際にロードし、受信、Purge、Close/Open、チャンネル列挙、範囲外の選局要求を検査しました。Purgeの初期測定値は47msでした。DLL・Goホスト・WinUSBを含む実機試験で、TVTest/EDCBの画面操作を使った試験ではありません。

WinSCardの30秒試験では、内蔵リーダーの列挙、T=1接続、B-CAS初期設定条件APDU、共有中の排他接続拒否、トランザクション、Purge後のカード通信、チューナーを閉じた後のカード単独通信を確認しました。APDUとカード応答本体は記録していません。

| 版 | 同時受信中のAPDU回数 | TSの同期 / TEI / continuity | 結果 |
| --- | --- | --- | --- |
| x64 | 278 | すべて0 | PASS |
| x86 | 276 | すべて0 | PASS |

x64の同時通信を300秒へ延長した試験もPASSでした。2,768回のAPDU通信と並行して647,545,132バイトを受信し、TSの同期・TEI・continuityの各エラーは0、TSIDは32224のみでした。Purge後の追加受信とカード通信、チューナー終了後のカード通信も成功しました。この試験後、BonDriverの残数出力ポインター省略時のAPI互換性とINFINITE待機の上限を調整し、配布用ビルドで短い試験を再実行しています。

## 自動試験・移植確認

Goの単体試験88件と `go vet ./...` が通っています。coax由来のFR30シミュレーター、ブリッジ、復調器、ISO7816、USBの試験に加え、キャッシュ選局と失敗時の破棄、期限切れの入力、階層別のインターリーブ、TS継続性・PAT CRC、IPC長の上限を検査しました。

Windows x64/x86のBonDriver・WinSCard・ホストをビルドしました。Linux amd64向けの受信CLIとホストもクロスビルドを確認しました。Linux実機での受信、macOS向けビルド・実機受信は未確認です。

WinSCardのエクスポート80個は、検証環境のSystem32版と名前・ordinalが一致しました。

配布用バイナリーの最終確認では、BonDriverの受信・Purge・13chでの選局失敗（610ms）・18/20chの往復・再オープンがPASSでした。残数出力ポインターを省略した呼び出しも成功しました。x64/x86のWinSCardも5秒の同時受信試験を再実行し、それぞれ46/47回のAPDU通信、TSエラー0、終了後のカード通信を確認しました。

## まだ確認できていない条件

- TVTestの実画面、EDCBでの予約録画、既存CAS/B25モジュールを通した放送の復号
- 数時間〜数日間の連続録画と、CPU・ディスク・USBへ負荷をかけた状態
- アンテナ条件を変えた比較、減衰器による弱電界試験、過大入力、受信中のロック喪失後の自動回復（現状配線の弱めの22chについては後述の追加検証を実施）
- USBの物理的な抜去・再接続、B-CASの抜去・再挿入
- 多数のカード接続やトランザクション待機が重なる場合
- 別プロセス間での同じUSB機器・内蔵カードの共有

上記の初版検証だけでは、先行実装で感じられた「受信のつかみの悪さ」の原因特定には至っていませんでした。後述の22ch追加検証で探索開始前の待機不足による失敗を特定・修正しました。px4_drvと同等の長期安定性を保証するものではなく、確認した条件での結果です。

## 22chの選局失敗修正後の追加検証

2026-10-27（日本時間）。[原因の比較調査](tune22-investigation.md)に基づき、FFT自動探索を始める直前に90msの待機を追加しました。ガード間隔探索、キャッシュを使う手動選局、通常の10msステップは維持しています。

診断専用版ではなく、修正後にビルドした`dist/x64`と`dist/x86`で確認しました。

| 条件 | 結果 |
| --- | --- |
| 22chを毎回開き直して初回選局、各1秒受信 | 5 / 5成功、選局2,530～2,780ms（初回校正を含む） |
| 13→18→19→20→21→22→23chを3周、各1秒受信 | 21 / 21成功。最初の7回は自動探索、残り14回はキャッシュ使用 |
| キャッシュ使用時の選局 | 997～1,183ms |
| 22chの30秒受信 | 344,740パケット、TEI・連続性・不正TS・PAT CRC・受信中の同期喪失はすべて0、空受信タイムアウト0 |
| x64 BonDriver公開APIで22ch | 選局・受信・Purge・Close/Open成功、PASS |
| x86 BonDriver公開APIで22ch | 選局・受信・Purge・Close/Open成功、PASS |

初回選局5回と反復切替21回の受信検査もTSエラー0でした。22chのTSIDは32708でした。Goの全テストと`go vet ./...`も成功しています。追加した回帰テストは、安定化前のFFT探索開始を拒否する模擬デバイスを用い、待機が探索開始より前にあることと、ガード間隔探索に追加待機が入らないことを検査します。
