# 22ch選局失敗の実機調査

2026-10-27（日本時間）。接続済みSony CECH-ZD1 J、Windows x64、既存のアンテナ配線で調査した。対象は物理13、18、19、20、21、22、23ch。22chの指定周波数は527,142,857 Hz。

## 結論

今回再現した22chの選局失敗には、FFT自動探索の開始前の待機不足が大きく関係している。通常の10ms刻みではFFTを2Kと判定して後続のガード間隔探索で失敗する一方、FFT探索の開始直前だけ90ms追加すると8Kと判定され、毎回機器を開き直した5試行すべてでフルセグ受信できた。

以下は修正前に行った診断用バイナリーによる比較であり、比較時点では配布用DLL・ホスト・CLIや製品コードの変更は行っていない。その後、条件Dの待機を製品コードへ反映した。修正後の結果は`docs/validation.md`に記録する。アナログ回路、AGC、復調器内部のどの安定化が必要なのかまでは特定していない。90msが必要最小値とも、すべての受信環境で十分とも断定できない。

## 観測結果

通常版で7チャンネルを順番に3周し、成功時に各2秒受信した。

| 物理ch | 選局成功 / 試行 | 成功時CNR（dB） |
| --- | --- | --- |
| 13 | 2 / 3 | 23.01～23.94 |
| 18 | 2 / 3 | 21.30～21.49 |
| 19 | 1 / 3 | 21.82 |
| 20 | 3 / 3 | 23.12～23.86 |
| 21 | 2 / 3 | 21.64～22.33 |
| 22 | 0 / 3 | ロックせず取得不可 |
| 23 | 3 / 3 | 23.38～25.22 |

22chの強度推定値は約−58dBmで、他局より低めだった。ただしこの値は別のDiB8000搭載基板由来の換算表を使っており、校正された実測電力ではない。選局成功後の22chのCNRは約20.5～21.1dBだった。弱さが失敗しやすさに影響する可能性はあるが、アンテナ条件を変えていないので因果関係は未確定。

## 待機箇所の比較

各条件5回、毎回プロセスと機器を開き直し、キャッシュを空にして22chを選局した。条件A→B→Cを交互に5回、その後Dを5回行った。成功した場合は各1秒TSを検査した。

| 条件 | 変更点 | 成功 / 試行 | FFT判定 |
| --- | --- | --- | --- |
| A | 通常の最小10ms待機 | 1 / 5 | 失敗4回は2K、成功1回は8K |
| B | 最小待機を全体に100msへ延長 | 5 / 5 | 全回8K |
| C | 通常10ms、FFT相関値の読取り直前だけ90ms追加 | 0 / 5 | 全回2K |
| D | 通常10ms、FFT探索の開始直前だけ90ms追加 | 5 / 5 | 全回8K |

同一セッションでの補助試験では、Aが0/10、Bが10/10成功した。ただしBの2回目以降9回はTMCCキャッシュを再利用しており、自動探索の成功率には数えない。

失敗には`failure-state-31`が記録され、FFT判定の後、ガード間隔の自動探索が失敗を通知する経路だった。10秒の外側タイムアウトで打ち切られたわけではない。多チャンネル試験の22chは約577～589msで失敗した。

成功した短時間試験ではTEI、連続性エラー、不正TS、PAT CRC異常、受信中の同期喪失はいずれも0だった。22chのPAT TSIDは32708。

条件Dの追加30秒受信でも、344,740パケットを受信し、TEI・連続性・不正TS・PAT CRC・受信中の同期喪失はすべて0、空受信タイムアウト0だった。選局開始から最初のTSまでは2,529ms（初回校正を含む）。これは長時間や受信条件変動に対する保証ではない。

## 実装上の場所と解釈

- `internal/coaxd/demod/dib8096/dib8000_tune.go`の`minTuneStep`は10ms。
- `tune()`の`demodStart`が周波数・帯域などを設定し、`demodSearchNext`が`autosearchStart()`を呼ぶ。条件DはFFT探索に限り、この呼出し直前に`state.msleep(90)`を追加した。
- `demodStep2`が相関値を比較して2K / 4K / 8Kを選ぶ。診断ログの`fft-choice-0`は2K、`fft-choice-2`は8Kを表す。
- 参照元の[Linux DiB8000ドライバー](https://github.com/torvalds/linux/blob/master/drivers/media/dvb-frontends/dib8000.c)では、選局ループの次のコールバック時刻まで`msleep(100)`で待つ。Go移植版の短い待機では同じ実時間を保証していない。

読取り直前の待機では回復せず、探索開始直前の待機で回復したため、「相関値を読むタイミングだけ早すぎる」よりも、「探索を始める前の安定化時間が足りない」という説明が今回の比較に合う。内部の物理機構を直接測定した結論ではない。

修正は、すべての状態を100msへ遅くする方式ではなく、FFT自動探索の開始前に限って90ms待つ方式を採用した。タイムアウト・キャンセルを扱う既存の待機経路を使う。他局への切替、初回校正、キャッシュ経路とBonDriver APIで実機確認する。無信号からの復帰は従来の自動試験に加え、必要に応じて受信できない物理チャンネルを指定して確認する。
